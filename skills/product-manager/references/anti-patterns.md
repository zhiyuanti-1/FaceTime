# 反模式清单（12 条）

> 每一条都是真实踩过的。用法：写文档时对照「症状」自检；被用户打回时先看「根因」，别急着改措辞。

---

## 1. 用示例冒充定义

| | |
|---|---|
| **症状** | 文档里出现"预设 A=20/B=15/C=10"，读者当成产品规则去实现；后来想改，被反问"这不是你定的吗" |
| **根因** | 为了让文档具体，把举例写成了配置 |
| **纠正** | 示例必须显式标注：「仅示例，可删，改它不算需求变更」。真正的规则写成"权重由运行时配置提供" |
| **自检** | 这个数字被删掉，文档还成立吗？成立 → 它只是示例 |

---

## 2. 把可选项写成必需

| | |
|---|---|
| **症状** | "必须部署代理服务"、"必须引入队列"，而用户只是本地单人使用 |
| **根因** | 按最坏情况设计，忽略了真实使用场景 |
| **纠正** | 先问"谁用、在哪用、给谁看"，再问"最坏会怎样"。按场景给方案 A/B/C，标出推荐项而不是唯一项 |
| **自检** | 这个组件能不能删掉还让用户完成主流程？能 → 它不是必需 |

---

## 3. 用人日冒充工期

| | |
|---|---|
| **症状** | "共 45 人日 → 2 人 4 周"，然后被现实打脸 |
| **根因** | 传统排期惯性；忽略了联调、内容生产、真机调参 |
| **纠正** | 人日只用于**排序**（谁先做、哪块重）。工期由"卡点"决定：第三方联调、内容产能、真机调试 |
| **自检** | 这个估计能不能被一次实测推翻？能 → 它是卡点，不是工期 |

---

## 4. 一处定义，多处副本

| | |
|---|---|
| **症状** | 同一个阈值在 3 份文档表述不同，实现方按最旧的那份写 |
| **根因** | 每份文档都"顺手再写一遍" |
| **纠正** | 一处定义 + 其余引用（"见 §X"）。改完跑一次全文关键词搜索，确认没有第二份 |
| **自检** | 搜关键词，命中 >1 处且写的是规则 → 有副本 |

---

## 5. 算例不自验

| | |
|---|---|
| **症状** | "4 个各 1 道，已经满 5 道，剩下的为 0" —— 数都对不上 |
| **根因** | 写的时候凭直觉，没有真算一遍 |
| **纠正** | 算例必须手算，并落成可执行断言（单测/脚本）。算例错了比没有算例更糟 |
| **自检** | 我把这个表照着算一遍，能得出文中的结论吗？ |

---

## 6. 汇报混层

| | |
|---|---|
| **症状** | 进度表里一半是"建表完成、驱动验证、workspace 落地"，业务方看不懂也不知道产品到哪了 |
| **根因** | 手上只有技术信息，直接搬了上来 |
| **纠正** | 业务表只写"用户能不能用"；技术进展单列 ≤3 行并链到技术文档 |
| **自检** | 这一行，用户能点一下验证吗？不能 → 移到技术节 |

---

## 7. 按模块排期

| | |
|---|---|
| **症状** | 仓储 → 组卷 → 音频 → AI → 报告，全部做完才第一次看见产品 |
| **根因** | 技术上更"整齐" |
| **纠正** | 按竖切里程碑排，每个里程碑结束时用户能完整走一遍 |
| **自检** | 这个里程碑的验收语是"用户能做 X"还是"模块写完了"？ |

---

## 8. 过度设计先行

| | |
|---|---|
| **症状** | 单人本地产品先上队列、多租户、监控、对象存储 |
| **根因** | "迟早要做" |
| **纠正** | 写进"非目标"，给触发条件（如"并发 >50 或对外分享时再做"） |
| **自检** | 不做它，这版能交付吗？能 → 它是下一版 |

---

## 9. 只给建议，不给文档

| | |
|---|---|
| **症状** | 回复里全是"建议考虑…""可以考虑…"，开发拿着无法开工 |
| **根因** | 怕写死担责 |
| **纠正** | 写字段、写枚举、写阈值、写错误码。写错就改文档，成本远低于"每人猜一套" |
| **自检** | 开发看完能直接开工吗？还需要问我几次？ |

---

## 10. 用提问代替交付

| | |
|---|---|
| **症状** | 一轮回复 8 个问题，用户答完又冒出 6 个 |
| **根因** | 想一次问清 |
| **纠正** | 最多问 3 个"会改变结构"的问题，其余给默认值 + 假设声明，先交付再迭代 |
| **自检** | 这些问题的答案会改变文档结构吗？不会 → 用默认值 |

---

## 11. 只增不减

| | |
|---|---|
| **症状** | 文档从 10 份长到 70 份，没人知道哪份作数 |
| **根因** | 没有退役机制 |
| **纠正** | 新建必须先回答"取代谁"。合并后旧文件进 `archive/`，并在进度文档记映射 |
| **自检** | 这份新文档让总数变成了几份？超过 5 份就该先合并 |

---

## 12. 改完不同步

| | |
|---|---|
| **症状** | 代码按新口径写了，文档还是旧的；下次有人按文档做，又错一遍 |
| **根因** | 文档不在"交付物"里 |
| **纠正** | 改代码的同一批改动里包含文档；交付前跑链接检查 + 关键词扫描 |
| **自检** | 这次改动涉及哪份文档？改了没有？ |

---

## 一页速查

| # | 一句话 |
|---|---|
| 1 | 示例要标"可删" |
| 2 | 能删还成立的，不是必需 |
| 3 | 人日排顺序，不排工期 |
| 4 | 一处定义，其余引用 |
| 5 | 算例必须真算 |
| 6 | 业务表只写用户能感知的 |
| 7 | 里程碑验收"用户能做 X" |
| 8 | 不做也能交付的，就是下一版 |
| 9 | 写死比写虚便宜 |
| 10 | 问 ≤3 个，其余给默认值 |
| 11 | 新增前先问取代谁 |
| 12 | 文档跟代码同一批交付 |
