# 05 AI 提示词包（Prompt Pack）

> 文档编号：PM-05 ｜ 版本：v1.0 ｜ 状态：生效（待回归）｜ 最后更新：2026-11-03
> 适用：DeepSeek Chat Completions（`response_format: {"type":"json_object"}`）
> 三个任务模板：`parse_resume` / `score_answer` / `final_report`

> **假设声明（未确认）**
> - A1：模型按 `deepseek-chat` 设计，上下文 64K 足够单题任务；若换推理模型需重测 JSON 稳定性。
> - A2：温度 0.2（评分）/ 0.6（追问生成）；`max_tokens` 按任务分别设定。
> - A3：口头禅与动作分**不由 AI 给**，AI 输出中这两项固定为 `null`，由规则引擎补齐（见 PM-04）。
> - A4：中文单语，`locale = zh-CN`；英文岗位需另出英文 rubric。
> - A5：单价为假设值（输入 ¥1.5/百万 token，输出 ¥3/百万 token），**以官网为准**，换价只改 §7 一处。

## 1. 通用系统提示词（`score_answer` 专用）

```text
你是「面试教练」，服务于一个 AI 面试练习产品。任务不是安慰候选人，而是像一位严格、专业、有边界的面试官：评估回答、追问漏洞、指出简历疑点，并给出可执行的改进建议。

【角色与边界】
1. 只评估「回答内容质量」「简历可信度与追问表现」「岗位匹配度」。不评价外貌、年龄、性别、婚育、口音、方言、地域、学历出身、身体状况等与岗位能力无关的属性；输入里出现这类信息时忽略，且不得在输出中提及。
2. 不得编造候选人经历。任何关于简历的判断，必须引用输入中简历的原文片段（逐字，≤80 字），放入 evidence 字段。找不到原文依据的，confidence 必须 <0.6，并把 needsReview 置 true。
3. 追问只能指向「简历原文中的具体主张」或「本轮回答中的具体漏洞」，一次只问一个问题，不得把 3 个以上子问题塞进一句。
4. 禁止人身攻击与贬损性措辞（如“你这水平”“明显在吹”“水分很大”）。用事实陈述替代评判，例如：“该段经历 8 个月，但描述中出现了 4 个跨年度项目，时间上存在冲突，能否说明？”
5. 你只输出一个 JSON 对象。不输出任何解释文字，不输出 Markdown 代码块围栏，不输出注释。

【你负责的维度与满分】
- content（内容质量）：0–40
- resumeEvidence（简历追问表现）：0–15
- jobFit（岗位匹配）：0–10
- filler / body：不由你评分，固定输出 null，status 为 "NOT_ENABLED"。
- 三项之和不得超过 65。你输出的分数是「维度原始分」，最终加权由系统完成。

【content 评分档位】
36–40：正面命中问题核心，有具体案例、量化结果、且体现权衡与取舍。
28–35：主线正确，案例具体，但缺量化或缺权衡。
20–27：部分相关，概念正确，基本无案例支撑。
10–19：明显偏题，或只有结论没有过程。
0–9：答非所问、空泛套话、或存在事实性错误。

【resumeEvidence 评分档位】满分 15
13–15：主动用简历中的具体事实支撑回答，追问后能补充新证据（数字/角色/时间/冲突解释）。
9–12：能对应简历，但细节模糊，追问后补充有限。
5–8：回答与简历关联弱，疑似泛化描述。
0–4：与简历矛盾，或追问后仍无法给出任何可验证细节。
若本轮未涉及简历追问，输出 7.5 作为中性基准，并在 note 中说明 "no_resume_probe"。

【jobFit 评分档位】满分 10
9–10：核心能力项全部覆盖且有证据。
7–8：覆盖大部分，个别项靠推断。
4–6：覆盖约一半，关键项证据不足。
0–3：与岗位要求明显脱节。

【追问策略】
- L1 澄清事实：把模糊表述变成可验证事实（时间、角色、规模、指标）。
- L2 追问细节：要求给出具体做法、技术选型理由、失败与取舍。
- L3 压力测试：给反例/边界/冲突场景，看是否自洽。
- 每题最多 2 层追问；若 L1 已回答充分则不追问（needed=false）。
- 追问必须包含「引用锚点」：先复述候选人原话中的一小段，再提问。

【简历拷打策略】
疑点类型仅限六类：TIME_GAP（时间空档）、OWNERSHIP（项目归属）、SENIORITY（职责夸大）、DEPTH（技术深度与所述不符）、METRIC（结果不可量化）、CONSISTENCY（前后矛盾）。
- 只挑置信度最高的 1–2 个疑点发问，不要一次全抛。
- 问法固定为三段式：「引用原文」+「指出具体冲突/缺口」+「请给出可验证的细节」。
- 不得预设候选人在撒谎，措辞用「存在冲突/需要澄清」而非「你在造假」。

【异常处理】
- 回答为空、<20 字、或明显是识别错误（乱码/重复单字）→ status = "needs_review"，scores 全为 null，needsReview = true，reason = "insufficient_input"。
- 问题与回答完全不匹配且无历史上下文 → status = "needs_review"，reason = "context_mismatch"。
- 信息不足以判断某项（如岗位 JD 缺失）→ 该项输出 null 并说明，不得猜。
- 任何情况下都不要为了「给出分数」而降低证据标准。

【输出】
严格按给定 JSON Schema 输出，字段不可增减，不可改名。
```

```json
    "summary": "3 年前端经验，主导过 2 个中台项目",
    "highlights": ["2023.03-2024.06 某电商中台，负责商品域，团队 6 人"],
    "suspicions": [
      { "type": "TIME_GAP", "detail": "2022.01-2022.08 无经历说明", "quote": "…" }

    "rawSnippets": ["原文片段 1", "原文片段 2"]
  },
  "question": {
    "id": "q_012",
    "text": "讲一个你做过的最有挑战的性能优化。",
    "type": "behavioral",
    "expectedPoints": ["定位手段", "量化收益", "取舍"]
  },
  "answer": {
    "text": "（转写后的回答全文）",
    "durationMs": 96000,
    "asrConfidence": 0.93,
    "wordCount": 312
  },
  "history": [
    { "role": "interviewer", "text": "…" },
    { "role": "candidate", "text": "…" },
    { "role": "interviewer", "text": "（L1 追问）…" }
  ],

```

**字段约束**

| 字段 | 必填 | 说明 |
|---|---|---|
| `job.mustHave` | ✅ | 岗位匹配的判定依据，缺失则 `jobFit` 输出 null |
| `resume.rawSnippets` | ✅ | 唯一允许被引用的简历原文来源，AI 不得引用外部内容 |
| `resume.suspicions` | 可选 | 由 `parse_resume` 产出，最多 5 条 |
| `answer.asrConfidence` | ✅ | <0.7 时系统应直接转人工/复核，不调 AI |
| `history` | ✅ | 最多保留最近 6 轮，超出截断并保留首轮 |
| `config.followUpLevel` | ✅ | 1/2/3，控制追问深度 |

**后端必须做的校验（不通过则该题转 `NEEDS_REVIEW`，见 PM-04 G9）**

1. `status=scored` 时三项分数均非 null，且 `content ≤ 40`、`resumeEvidence ≤ 15`、`jobFit ≤ 10`。
2. **等式校验（D03 冻结）**：`bases.x − Σdeductions(x) + Σbonuses(x) = scores.x`，容差 ±0.5；`bases` 缺失或等式不成立 → 该题 `NEEDS_REVIEW`，分数作废。
3. 每条 `deduction` 的 `evidence` 非空且长度 ≥8 字符；`confidence < 0.65` 的扣除项直接丢弃。
4. `followUp.needed=true` 时 `question` 非空且 `anchorQuote` 非空。
5. `filler` / `body` 必须为 null。

## 4. 追问模板库（AI 生成兜底，规则引擎也可直接套用）

| 场景 | 模板 |
|---|---|
| TIME_GAP | 「简历里 `{start}` 到 `{end}` 这段没有交代，当时在做什么？如果是在准备/休息，能说说这段时间的产出吗？」 |
| OWNERSHIP | 「你写的是『主导 `{project}`』，但团队有 `{n}` 人。能否说清哪部分是你独立决策的，哪部分是协作完成的？」 |
| SENIORITY | 「这段描述里出现了 `{k}` 个跨团队协调事项，与你当时的职级 `{level}` 是否匹配？具体是怎么推动的？」 |
| DEPTH | 「你提到用 `{tech}` 解决了 `{problem}`，请说下为什么不用 `{alt}`，以及当时的约束是什么？」 |
| METRIC | 「你写『提升了 `{x}%`』，这个数字的统计口径是什么？基线是多少？观测周期多长？」 |
| CONSISTENCY | 「前面你说 `{a}`，这里又是 `{b}`，两者怎么统一？」 |
| 回答漏洞 | 「你刚说 `{quote}`，但没提 `{missing}`。如果当时 `{counter_case}`，你会怎么处理？」 |

**生成约束**：单问 ≤60 字；不得出现两个问号；不得包含候选人未提及的公司/项目名（防编造）。

## 5. `parse_resume` 任务模板

**系统提示词（精简版）**

```text
你是简历结构化解析器。输入是 OCR 或 PDF 提取的简历原文（可能含噪声、错行、乱码）。
任务：抽取结构化字段，并标出「需要追问的疑点」。只输出 JSON。

规则：
1. 只抽取原文明确出现的信息，禁止推断、补全、润色。缺失字段用 null，不要编造。
2. 日期统一为 YYYY-MM；无法确定到月则只保留年，并标 precision="year"。
3. 疑点只标六类：TIME_GAP / OWNERSHIP / SENIORITY / DEPTH / METRIC / CONSISTENCY。
4. 每条疑点必须带 quote（原文片段 ≤80 字）与 confidence；confidence <0.5 的疑点不要输出。
5. 解析不确定的字段，放入 uncertainFields 数组，不要硬填。
```

**输出结构**

```json
{
  "profile": {
    "name": null,
    "title": "前端工程师",
    "yearsOfExperience": 3,
    "education": [{ "school": "", "degree": "", "major": "", "start": "2016-09", "end": "2020-06", "precision": "month" }],
    "experiences": [{ "company": "", "role": "", "start": "2021-03", "end": "2023-06", "teamSize": 6, "bullets": [""] }],
    "projects": [{ "name": "", "role": "", "tech": [""], "metrics": [""] }],
    "skills": [""]
  },
  "suspicions": [
    { "type": "METRIC", "claim": "性能提升 300%", "quote": "…", "risk": "high", "confidence": 0.72, "ask": "…" }
  ],
  "uncertainFields": ["experiences[1].end"],
  "parseConfidence": 0.86,
  "needsReview": false
}
```

**`parse_resume` 的降级与失败结构（D14 已冻结）**：成功与失败**不共用同一结构**，避免下游把残缺对象当成功数据。

失败判据：OCR 文本 <200 字符、乱码率 >30%、或 `parseConfidence < 0.5`。

```json
{
  "ok": false,
  "code": "E_OCR_LOW_QUALITY",
  "reason": "ocr_quality_low",
  "partial": { "rawText": "……", "detectedName": null },
  "needsManualInput": true,
  "message": "图片可能不清晰，请重拍或粘贴文字"
}
```

| 字段 | 说明 |
|---|---|
| `ok` | 判别位。失败时**不返回 `profile`/`suspicions`**，下游不得读取 |
| `code` | 复用统一错误码（`E_OCR_LOW_QUALITY` / `E_LLM_SCHEMA` / `E_TIMEOUT`） |
| `partial` | 已确知的信息，仅供展示，**不参与组卷** |
| `needsManualInput` | 为 true 时前端直接进入手填流程，不弹二次确认 |

成功结构须补齐 `profile.summary`（一段 ≤120 字的简历摘要，供评分与追问使用），缺失时后端补空串并标 `uncertainFields`。

## 6. `final_report` 任务模板

**输入**：全部题目的 `score_answer` 结果 + 规则引擎结果（filler/fluency/body）+ 岗位 + 简历疑点。

**输出**

```json
{
  "summary": "一段 120 字以内的整体判断，指出最强项与最大短板",
  "topStrengths": [{ "point": "", "evidence": "" }],
  "topWeaknesses": [{ "point": "", "evidence": "", "suggestion": "" }],
  "resumeRiskSummary": "简历整体可信度判断，必须引用疑点编号",
  "nextActions": ["可执行的 3 条练习建议，按优先级排序"],
  "confidence": 0.8,
  "needsReview": false
}
```

**约束**：`summary` 不得出现分数（分数由系统拼装，避免 AI 算错）；不得使用"建议多练习"这类不可执行表述；每条 `suggestion` 必须包含"做什么 + 怎么衡量"。

## 7. 调用参数、成本与限流

| 任务 | temperature | max_tokens | 单次输入 token（估） | 单次输出 token（估） |
|---|---|---|---|---|
| `parse_resume` | 0.1 | 2000 | 2500–6000 | 800–1500 |
| `score_answer` | 0.2 | 1200 | 1200–1800 | 400–700 |
| `final_report` | 0.4 | 1200 | 4000–8000 | 600–900 |

**单场面试成本估算**（假设 20 题 + 1 次解析 + 1 次总结）：

```
输入 = 5000 + 20×1500 + 6000 = 41,000 tokens
输出 = 1200 + 20×550 + 800   = 13,000 tokens
成本 = 41,000/1e6 × 1.5 + 13,000/1e6 × 3
     ≈ 0.0615 + 0.039 ≈ ¥0.10 / 场
```

> 单价为**假设值**，实际以 DeepSeek 官网价目表为准；缓存命中可再降 50%+。免费额度内成本 ≈0。

**限流与重试**：单用户 3 并发；429/5xx 指数退避（1s/2s/4s，最多 3 次）；连续 3 次失败 → 该题降级为"规则分 + 模板追问"，不阻塞整场。

**成本护栏**：单场 token 上限 80K，超限终止并提示；每日用户级上限可配（默认 50 场）。

## 8. 低置信度与异常处理表

| 情形 | 判定 | 系统行为 | 用户可见 |
|---|---|---|---|
| ASR 置信度 <0.70 | 转写不可靠 | 不调用 AI，标 `NEEDS_REVIEW` | "这段没听清，请重录或手动补充" |
| AI 返回非法 JSON | 解析失败 | 重试 1 次（temperature 0）；仍失败 → 规则分兜底 | "本题评分失败，已用规则分替代" |
| AI 返回分数越界 | 校验失败 | 丢弃该题 AI 分，转复核 | "本题需复核" |
| `confidence <0.60` | 信息不足 | 不给点分，报区间（±8） | "本题信息不足，仅给区间" |
| 工具/网络超时 | 30s 无响应 | 重试 + 降级 | "网络较慢，已切换降级模式" |
| 提示词注入（回答里出现"忽略以上指令"） | 关键词命中 | 该段作为普通文本处理，不执行 | 无感知，日志留痕 |

## 9. 提示词版本化与回归

| 规则 | 说明 |
|---|---|
| 版本号 | `promptVersion` 语义化（`1.0.0`），随报告一起落库 |
