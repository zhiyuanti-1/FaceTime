## 2. 概念模型

```
JobProfile ──topics权重──▶ Composer ──配额──▶ TopicPool × N ──抽题──▶ PaperPlan
                                ▲                                        │
ResumeProfile ──suspicions──▶ ProbeBuilder ──5道拷打题──────────────────┘
```

| 实体 | 职责 | 关键字段 |
|---|---|---|
| `TopicPool` | 一个知识点的题目集合 | `topicId`、`questions[]` |
| `Question` | 单题 | `id`、`topicId`、`difficulty`、`text`、`expectedPoints` |
| `JobProfile` | 岗位画像 | `role`、`level`、`topicWeights[]` |

| `ResumeProbe` | 简历拷打题 | `id`、`source`、`target`、`question`、`severity` |

| # | topicId | 名称 | 主要适用岗位 | 阶段 | 当前 | 上限目标 |
|---|---|---|---|---|---|---|
| 1 | `js` | JavaScript（含浏览器/事件循环） | 前端/全栈 | seed | 20 | 100 |
| 2 | `vue` | Vue | 前端 | seed | 20 | 100 |
| 3 | `react` | React | 前端 | seed | 20 | 100 |
| 4 | `html` | HTML / CSS / 布局 | 前端 | seed | 20 | 100 |
| 5 | `network` | 计算机网络 | 全岗位 | seed | 20 | 100 |
| 6 | `algorithm` | 数据结构与算法 | 全岗位 | seed | 20 | 100 |
| 7 | `database` | 数据库 | 后端/全栈 | seed | 20 | 100 |
| 8 | `os` | 操作系统 | 后端/全栈 | seed | 20 | 100 |
| 9 | `java` | Java / JVM | 后端 | seed | 20 | 100 |
| 10 | `engineering` | 前端工程化（Vite/Webpack/Git/CI） | 前端 | seed | 20 | 100 |
| — | `ts` | TypeScript | 前端/全栈 | **暂缺** | 0 | 100 |
| — | `behavioral` | 行为与项目复盘 | 全岗位 | **暂缺** | 0 | 100 |

**合计 200 题（10 池）**。`ts` 与 `behavioral` 留空：前者等真题库一起补，后者在本产品里优先由简历项目派生，不必单独成池。

**难度分布**：seed 阶段不强制（实际分布见 `index.json`）；curated 阶段要求 简单 30 / 中等 50 / 困难 20。

**替换真题库的验收线**：任意池达到 100 题 + `stage: "curated"` + `verified: true`，即自动从"占位"升级为"正式"，组卷降级告警随之消失。

## 4. 题目数据结构

```ts
type TopicId = 'js' | 'vue' | 'react' | 'html' | 'network'
             | 'algorithm' | 'database' | 'os' | 'java' | 'engineering'
             | 'ts' | 'behavioral';        // 后两个暂缺，保留枚举位

type Difficulty = 1 | 2 | 3;          // 1 简单 2 中等 3 困难
type AnswerMode = 'oral' | 'oral_scenario';

/** 文件级（一个池一个文件），stage 决定能否抽题与是否告警 */
interface TopicBankFile {
  topicId: TopicId;                   // 池级声明，题目里不重复写
  name: string;
  stage: 'seed' | 'curated';          // seed=占位可替换，curated=正式
  version: number;
  questions: Question[];
}

interface Question {
  id: string;                 // `q_${topicId}_${4位序号}`，如 q_vue_0007
  difficulty: Difficulty;
  mode: AnswerMode;
  text: string;               // ≤120 字，一个主题；问号 ≤2 个
  expectedPoints: string[];   // 3–6 条，评分与追问的锚点，单个 ≤60 字
  followUpHints?: string[];   // 可选，L2 追问提示
  tags: string[];             // 如 ['响应式','nextTick']
  timeLimitSec: number;       // 120 基础 / 180 进阶
  verified: boolean;          // 是否经人工校验
  // topicId 与 contentHash 不由人工填写：
  //   topicId 由加载器从文件级注入；contentHash 由构建脚本按 text 计算
}
```

**加载约定**：`bankLoader` 读文件后补 `topicId`、按 `text` 计算 `contentHash`（sha1 前 12 位），再交给组卷器。这样内容同学改题不会因为忘写 `topicId` 而校验失败。

**校验规则（`scripts/validate-bank.mjs` 强制，`--check` 用于 CI）**

| # | 规则 | 处理 |
|---|---|---|
| V1 | `id` 全局唯一且符合 `q_<topic>_<4位>` | 构建失败 |
| V2 | `text` 含 1–2 个问号（同一主题允许多问一答） | 构建失败（0 个仅告警） |
| V3 | `expectedPoints` 数量 3–6，单个 ≤60 字 | 构建失败 |
| V4 | 池内 `text` 归一化后重复 | 构建失败 |
| V5 | 跨池题干互相包含 | 告警，人工确认 |
| V6 | `difficulty` 分布偏离目标 >20% | **仅 curated 告警**（seed 不检查质量） |
| V7 | `verified=false` | seed 阶段仍可抽题；curated 阶段不可 |
| V8 | 题量 ≠ 20（seed）/ ≠ 100（curated） | 告警 |

## 5. 岗位画像与权重

### 5.1 数据结构

```ts
interface TopicWeight {
  topicId: TopicId;
  weight: number;      // 相对权重 0–100，非题量；0 表示本场不出
  minCount?: number;   // 显式下限，优先级高于 weight
  maxCount?: number;   // 显式上限，默认 2
}

interface JobProfile {
  id: string;              // 'fe_senior' | 'fe_junior' | 'be_java' | 'custom'
  role: string;            // 展示名：高级前端工程师
  level: 'junior' | 'mid' | 'senior';
  topicWeights: TopicWeight[];
  knowledgeCount: number;  // 默认 5
  probeCount: number;      // 默认 5
  orderStrategy: 'interleave' | 'block';
}
```

### 5.2 权重暂不锁定（当前状态：`pending`）

**决策状态**：算法按权重走已确定；**具体权重数值暂不定**。因此 1.0 的默认形态是：

| 形态 | 说明 |
|---|---|
| 默认进入 `custom`（自定义） | 打开设置页即是滑块面板，初始值来自 `presets/weights.example.json` |
| 预设仅作「示例配置」 | 下面三组只是 UI 的初始填充值，**不是产品定义**，随时可改可删，改它不算需求变更 |
| 权重持久化在本地 | 用户调完存 IndexedDB，下次沿用；导出/导入 JSON 便于你换岗位试 |
| 代码侧只认结构，不认数值 | `TopicWeight[]` 是契约；数值全部来自配置，禁止写死在算法里 |

| 示例配置（仅用于填充滑块） | 数值 |
|---|---|
| `example_fe` 前端示例 | js 20、vue 15、react 15、network 15、engineering 15、browser 10、css 5、behavioral 5 |
| `example_be` 后端示例 | java 30、database 20、network 15、algorithm 15、behavioral 10、engineering 10 |
| `example_blank` 空白 | 全部 0，由用户自己拖（首次使用默认走这个 + 顶部提示"请先设置各方向重要性"） |

**这样做的代价**：不做预设意味着新用户第一次要多花 1 分钟配置。若你后面觉得麻烦，再加预设只需改一个 JSON 文件 + 0 行代码。

### 5.3 关键交互

- 设置页展示 12 个滑块 + 实时提示「当前预计出题：Vue 1 题、网络 1 题…」。
- 权重总和 ≠100 不报错，内部归一化；但总和为 0 时禁用「开始面试」。
- 用户改权重后，实时重算配额并预览（不抽题），点「开始」才真正抽题。

## 6. 配额分配算法

### 6.1 主算法：最大余额法 + 约束

```ts
function allocate(count: number, items: TopicWeight[]): Map<TopicId, number> {
  // 1. 过滤 weight=0
  // 2. 归一化：share_i = weight_i / Σweight
  // 3. 基础配额 quota_i = floor(count * share_i)
  // 4. 余额按小数部分降序补 1，直到 Σquota = count
  // 5. 应用 minCount / maxCount（默认 max=2）
  // 6. 若因上限导致缺口，回填给次高权重、未达上限的 topic
  // 7. 兜底：所有 topic 都达上限仍不足 → 放宽 maxCount 并记 warning
}
```

**设计意图**：5 道题时，权重的主要作用是**决定谁进前 5**，而不是 1:1 映射题量——权重 20 和 15 在 5 个位置下大概率都是 1 道。所以你给的例子会得到「每池各 1 道」。

### 6.2 算例（用你给的配置）

输入：`vue 20 / network 20 / react 20 / engineering(vite) 20 / java 10`，`count = 5`。

| 步骤 | 计算 | 结果 |
|---|---|---|
| 归一化 | 20/90 = 0.2222（×4），10/90 = 0.1111 | — |
| 基础配额 | `floor(5×0.2222)=1` ×4；`floor(5×0.1111)=0` | vue1 / net1 / react1 / eng1 / java0 = **4 个** |
| 余额分配 | 空位 1 个；小数部分 java 0.5555 最高，其余 0.1111 | **java 补 1** |
| 最终 | — | **vue1 / network1 / react1 / engineering1 / java1 = 5 道** |

> **D06 已冻结的修正**：原文写「已满 5、java 为 0」是算错的——4 个 topic 各 1 道只占 4 个位置，第 5 个位置按最大余额法属于 `java`（0.5555 > 0.1111）。**结论反过来：这个配置下 java 会出 1 道，而不是 0 道。**
>
> 由此得出一条必须实现的规则：**余额补位后若仍不足 `count`**（例如所有 topic 都触达 `maxCount`），按「次高权重且未达上限」继续补，并允许同池出第 2 题；再不足则走 §9 的减题策略。**不允许无限重抽，也不允许返回少于 `count` 的题集却不告知。**
>
> 同权重（并列小数）一律按 `topicId` 字典序稳定排序，保证同种子可复现。

### 6.3 B 方案（备选，等你拍板）

若你的原意是「按权重从各池抽 20 道组成 90 道候选题，再从中精挑 5 道」，则算法改为：`候选池 = Σ(min(weight_i, poolSize) )` → 二次筛选（难度分层 + 去重 + 覆盖度打分），排期增加 **2 人日**。默认走 A 方案。

### 6.4 算例：8 个 topic、count=5（前端取向）

| topic | weight | share | base | 余数 | final |
|---|---|---|---|---|---|
| js | 20 | 0.20 | 1 | 0.00 | 1 |
| vue | 15 | 0.15 | 0 | 0.75 | 1（余数并列第 1） |
| react | 15 | 0.15 | 0 | 0.75 | 1（余数并列第 2） |
| network | 15 | 0.15 | 0 | 0.75 | 1（余数并列第 3） |
| engineering | 15 | 0.15 | 0 | 0.75 | 1（余数并列第 4） |
| html | 10 | 0.10 | 0 | 0.50 | 0 |
| algorithm | 10 | 0.10 | 0 | 0.50 | 0 |
| java | 0 | 0.00 | 0 | 0.00 | 0（权重 0 直接排除） |

合计 5 道。四个 0.75 并列，按 `topicId` 字典序（engineering < network < react < vue）分配这 4 个位置，只不过四者同权同余数、结果都是一道，排序只影响可复现性。

## 7. 抽题算法

```ts
function drawQuestions(pool: TopicPool, n: number, ctx: DrawContext): Question[]
```

| 参数 | 说明 |
|---|---|
| `seed` | 会话 ID 派生的种子，使用 `mulberry32` 可复现随机 |
| `level` | 岗位级别 → 难度权重：junior(1:0.5,2:0.4,3:0.1)、mid(0.3,0.5,0.2)、senior(0.15,0.45,0.4) |
| `exclude` | 最近 3 场已出过的题（`recentQuestionIds`，存 localStorage） |
| `seenPenalty` | 历史出过但非最近 3 场：降权 0.3 |
| 去重 | 抽题后做 `expectedPoints` 重合度检查，>70% 视为重复，重抽 |

**可用题集定义（一条，别的地方不要另写）**：

```
usable(pool) = pool.stage === 'seed'
             ? pool.questions                      // 占位题库：全部可用
             : pool.questions.filter(q => q.verified)  // 正式题库：只用手工校验过的
```

seed 池被抽中时，`PaperPlan.warnings` 必须追加一条：`「<topic> 当前为占位题库（20 题），质量未校验」`，报告页展示。**这是诚实性要求：不能让用户以为这些题是精编的。**

**约束**：
1. 5 道八股中，覆盖 topic 数 ≥3（配额算法一般已满足，作为兜底断言）。
2. 首题必须 `difficulty=1`（破冰）。
3. 同池内不得连出 2 道同 `tags` 主标签的题。
4. 抽不满（池内可用题 < 配额）→ 见 §9 降级。

## 8. 组装：5 八股 + 5 拷打

### 8.1 顺序策略

**默认 `interleave`**（八股与拷打交替，避免连续 5 道八股把人问崩）：

```
[1] 八股·易（破冰）
[2] 八股
[3] 拷打①
[4] 八股
[5] 拷打②
[6] 八股
[7] 拷打③
[8] 八股
[9] 拷打④
[10] 拷打⑤（收尾：项目总结/反问）
```

**备选 `block`**：5 八股 → 5 拷打（模拟真实一轮技术面）。设置页可切换。

### 8.2 拷打题生成（不走题库，走简历）

```ts
interface ResumeProbe {
  id: string;                       // probe_1 … probe_5
  source: 'suspicion' | 'project' | 'gap_fill';
  target: string;                   // 指向简历章节/原文片段；gap_fill 时为 'general'
  suspicionType?: SuspicionType;    // TIME_GAP / OWNERSHIP / …
  question: string;                 // ≤60 字，单问句
  anchorQuote: string | null;       // 简历题必须非空；gap_fill 必须为 null（D07 冻结）
  severity: 1 | 2 | 3;              // 高 3 中 2 低 1
  confidence: number;
}
```

**生成优先级**：

| 顺位 | 来源 | 规则 |
|---|---|---|
| 1 | `suspicions` 按 `severity × confidence` 降序 | 取前 3，且疑点类型尽量不重复 |
| 2 | 项目深挖 | 从 `projects[]` 选最相关 2 个，套模板（见下） |
| 3 | `gap_fill` 兜底 | 疑点与项目都不足时，用通用深挖模板补齐到 5 道 |

**项目深挖模板**（固定 4 选 2，不调 AI，保证离线可用）：

| 模板 | 题面 |
|---|---|
| P1 角色 | 「在 `{project}` 里你具体负责哪一部分？团队几个人，怎么分工的？」 |
| P2 难点 | 「`{project}` 最难的技术点是什么？当时卡了多久，最后怎么解决的？」 |
| P3 取舍 | 「如果重做一次 `{project}`，你会改哪个技术决策？为什么？」 |
| P4 结果 | 「`{project}` 上线后的效果怎么衡量的？有没有具体数字？」 |

**兜底模板（`gap_fill`）**：

| 模板 | 题面 |
|---|---|
| G1 | 「挑一段你最有成就感的经历，说清背景、你的动作、结果。」 |
| G2 | 「讲一次你和同事意见不一致的经历，最后怎么定的？」 |
| G3 | 「最近半年你主动学了什么？怎么验证学懂了？」 |

**硬约束（D07 已冻结）**：

1. 拷打题不得编造简历中没有的公司/项目/技术名。
2. **两类题必须分开计数**：`source ∈ {suspicion, project}` 是**简历题**，`anchorQuote` 必须非空；`source = 'gap_fill'` 是**通用深挖题**，`anchorQuote` 必须为 `null`。
3. 简历为空（或解析失败）时，5 道全部是通用深挖题 → `probeCount` 里的「简历题」记 0，报告显示「简历题 0 道 / 通用深挖 5 道」，**不得假装是简历拷打**，也不得为了凑数编造引用。
4. 任何情况下不得生成空 `anchorQuote` 的简历题；引用必须逐字来自 `resume.rawSnippets`。

## 9. 题量不足与降级

**级联顺序（D12 已冻结，必须按此顺序，不许跳步或无限重抽）**

| 级 | 情形 | 处理 | 用户可见 |
|---|---|---|---|
| L1 | 某池可用题 < 配额 | 缺口转给次高权重、未达 `maxCount` 的池 | 「该知识点题量不足，已补充其它方向」 |
| L2 | 所有池都触达 `maxCount` 仍不足 | 放宽 `maxCount` 到 2，允许同池出 2 题 | 「本场同方向题目偏多」 |
| L3 | 放宽后仍不足 | **减题**：`count` 逐级下调（5→4→3 八股），但总题量不低于 **6 题**；减少的数量记入 `warnings` | 「题量不足，本场共 X 题」 |
| L4 | 减到 6 题仍凑不出，或覆盖主题 <2 个 | **拒绝开考**，返回可操作提示，不生成残卷 | 「题库不足，请更换方向或等待题库更新」 |
| — | 池未上线（如 `ts`，题量为 0） | 该 topic 自动 `weight=0` 并置灰 | 「TypeScript 题库建设中，暂不可选」 |
| — | 简历解析失败（无 suspicious 且无 projects） | 5 道全用 `gap_fill`，**不计为简历题**（见 §8.2 D07） | 「简历信息不足，已切换通用深挖题」 |
| — | 简历解析部分失败（有 projects 无 suspicions） | 3 道项目深挖 + 2 道通用深挖 | 正常，不额外提示 |

**三条硬规则**

1. **重抽上限**：单题去重重抽最多 5 次，超限即视为该池不可用并进入下一级，禁止死循环。
2. **不静默减题**：L3 减题必须在开考前弹一次确认（或在开始页明示题量），报告里 `warnings` 保留记录。
3. **≥3 主题约束降级**：`count` 降到 4 以下时，主题数约束从 ≥3 放宽到 ≥2，并在 `warnings` 写明「主题覆盖不足」。

`PaperPlan.warnings: string[]` 必须把这些降级事实带给报告页，报告不能假装「一切正常」。

## 10. 题库生产与验收标准

| 项 | seed 阶段（当前） | curated 阶段（后续） |
|---|---|---|
| 单池题量 | 20 | 100 |
| 难度分布 | 不要求 | 1:2:3 = 30:50:20，允许 ±20% |
| 答案要点 | 3–6 条，语句通顺即可 | 必须可判定（"说出 X 与 Y 的区别"而非"理解 X"） |
| 去重 | 池内 0 重复 | 池内 0 重复；跨池 ≤5% 语义重合 |
| 时效 | 不要求 | 覆盖近 2 个大版本（Vue 3 / React 18+） |
| 人工校验 | 不要求（`verified=false` 允许） | 100% `verified=true` |
| 抽题覆盖 | 连抽 50 次，单题出现次数差异 ≤2 倍 | 连抽 100 次，概率差 ≤3 倍（避免"死题"） |

**产能**：seed 200 题 ≈ 4 人时（AI 起草 + 人工扫一遍）；curated 1000 题 ≈ 100 人时（6 分钟/题含校验）。

**替换路径（不改代码）**：把 `packages/content/bank/<topic>.json` 换成新文件 → 改 `stage: "curated"` → `verified` 全置 true → 跑 `node scripts/validate-bank.mjs` 重新生成 `index.json`。组卷器自动从"占位"切到"正式"，报告里的占位告警消失。

## 11. 存储与打包

| 项 | 方案 |
|---|---|
| 存放 | `packages/content/bank/<topicId>.json`，按池拆文件，便于并行编辑与按需加载 |
| 加载 | 首屏只加载 `index.json`（池元信息：题量、难度分布、版本）；进入组卷时按需 `import()` 目标池 |

| 版本 | `bankVersion` 随构建注入，写入报告，便于回溯"这题当时是哪个版本" |
