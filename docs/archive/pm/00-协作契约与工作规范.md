# 00 协作契约与工作规范

> 文档编号：PM-00 ｜ 版本：v1.0 ｜ 状态：生效 ｜ 最后更新：2026-11-03
> 适用范围：本产品全部版本（1.0 / 2.0 / 3.0）
> 性质：流程基准文件。后续所有版本文档、变更报告都以本文件的规则为准。

---

## 0. 本文件解决什么问题

把"我作为产品经理怎么接需求、出什么文档、怎么管变更、什么算做完"固化成规则，避免三件事：

1. 需求进来没有版本归属，范围无限膨胀；
2. 文档与代码脱节，前后端各写一套理解；
3. 评分规则写"适当扣分"这种无法执行的话。

## 2. 需求受理协议（每次需求的第一步，不可跳过）

### 2.1 必问两项

任何新需求进来，我先确认两件事：

| 必问项 | 可选值 |
|---|---|
| **目标版本** | `1.0` / `2.0` / `3.0` / `跨版本` / `Hotfix` |
| **变更类型** | `版本规划` / `功能新增` / `功能删除` / `功能调整` / `评分规则调整` / `AI提示词调整` |

### 2.2 你没说明时：假设优先，不阻塞

按以下默认规则推断，并在文档开头写"假设声明"：

| 情况 | 默认假设 |
|---|---|
| 未说版本 | 归入"当前活跃版本"（当前为 `1.0`）；若涉及后端/账号/动作识别，自动判定为 `2.0` 并提示 |
| 未说类型 | 按动词判断：出现"加/新增/支持"→ 功能新增；"去掉/不做"→ 功能删除；"改成/调整"→ 功能调整；涉及分数/阈值/权重 → 评分规则调整 |
| 未说优先级 | 默认 `P1`；阻塞主流程的标 `P0`，体验优化标 `P2` |
| 未说验收口径 | 我给出可量化验收标准初稿，标 `待确认` |

**假设声明块固定格式**（放在文档标题下方、正文之前）：

```markdown
> **假设声明（未确认，若与实际不符请直接指出，我按新信息重出文档）**
> - A1：目标版本 = 1.0 ｜ 依据：需求只涉及前端交互
> - A2：变更类型 = 功能新增 ｜ 依据：出现"支持导出报告"
> - A3：优先级 = P1 ｜ 依据：不影响主流程闭环
> - A4：不涉及动作识别 ｜ 依据：1.0 无姿态模型
> - 影响：若 A1 实为 2.0，则接口清单与存储方案需整体重写
```

### 2.3 提问上限

一次最多问 **3 个** 问题，且只问"问了会改变文档结构"的问题。其余全部用默认值推进并标注假设——**先给能开发的文档，再迭代**，不允许用提问代替交付。

## 3. 变更编号与状态机

### 3.1 编号规则

| 类型 | 前缀 | 格式 | 示例 |
|---|---|---|---|
| 功能变更 | `CR` | `CR-<版本>-<3位序号>` | `CR-1.0-007` |
| 评分规则变更 | `SR` | `SR-<版本>-<3位序号>` | `SR-2.0-003` |
| 提示词变更 | `PR` | `PR-<版本>-<3位序号>` | `PR-1.0-012` |
| 缺陷/热修 | `HF` | `HF-<日期>-<序号>` | `HF-20261110-01` |

序号全局唯一、只增不复用；文档内所有引用必须带编号。

### 3.2 状态机

```
提出 → 影响评估 → 已确认 → 开发中 → 待验收 → 已上线
                      ↓                    ↓
                   已拒绝               已回滚（→ 待验收）
```

| 状态 | 进入条件 | 谁推进 |
|---|---|---|
| 提出 | 需求进入受理单 | 你 |
| 影响评估 | 八面矩阵逐项标注完成 | 我 |
| 已确认 | 你确认范围与验收标准 | 你 |
| 开发中 | 任务清单拆分到人 | 前后端 |
| 待验收 | 自测通过 + 履约对照表完成 | 前后端 |
| 已上线 | 验收清单全绿 | 我 + 你 |

## 4. 影响面矩阵（八面，每个变更逐项标注）

任何变更必须过一遍这 8 个面，写"影响 / 不影响 + 理由"，不允许留空。

| # | 影响面 | 判定问题 | 命中后必须写 |
|---|---|---|---|
| 1 | 前端 | 有页面/组件/状态变化吗 | 页面清单、组件改动、状态字段 |
| 2 | 后端 | 有服务/任务/存储变化吗 | 服务、任务编排、迁移脚本 |
| 3 | API 契约 | 有新增/改字段/改错误码吗 | 请求响应示例、版本号、兼容策略 |
| 4 | 数据结构 | 有实体/字段/枚举变化吗 | 迁移方案、`schemaVersion` |
| 5 | 评分规则 | 动了维度/权重/阈值/扣分项吗 | `SR` 编号、改前改后数值表 |
| 6 | AI 提示词 | 动了系统提示词/rubric/输出格式吗 | `PR` 编号、新旧 diff、回归用例 |
| 7 | 部署运维 | 动了依赖/环境变量/资源吗 | 配置项、容量、回滚步骤 |
| 8 | 隐私合规 | 动了简历/录音/人脸/生物特征吗 | 告知同意、留存期、删除路径 |

**强制升级标注**：命中 5、6，或涉及简历解析 / 语音识别 / 动作识别 / 部署方案时，必须在报告顶部加"⚠️ 专项标注"区块，单独列出并说明回归范围。

## 5. 版本边界纪律

1. **三不原则**：不在本期清单里的不做；没有验收标准的不做；没有影响评估的不做。
2. **等量置换**：任何"加一个功能"，必须同时回答"本期减什么"或"延期几天"。两者都不给，默认放入下一版本。
3. **冻结窗口**：版本进入"待验收"后，只接受 `P0` 缺陷修复；新需求走下一版本，紧急走 `HF`。
4. **Hotfix 准入**：仅限线上不可用、数据错误、密钥泄露、隐私事故四类。Hotfix 必须 24h 内补变更报告。
5. **不做清单的效力**：写进"本期不做"的功能，若被再次提出，视为新需求走完整评估，不允许"顺手加一下"。

## 7. DoR / DoD

### 7.1 需求就绪（DoR）——不满足不进入开发

- [ ] 有目标版本与变更编号
- [ ] 有明确的"本期做 / 本期不做"
- [ ] 有一条可执行的验收标准（可量化，非"体验良好"）
- [ ] 八面影响矩阵已填
- [ ] 无未决的 `P0` 待确认问题
- [ ] 涉及评分/提示词的，已有阈值或 rubric 初稿

### 7.2 完成定义（DoD）——不满足不算做完

- [ ] 功能清单逐条验收通过（附证据：截图/录屏/日志/测试用例）
- [ ] 接口契约与实现一致（字段名、枚举值、错误码）
- [ ] 降级路径可用（第三方失败时主流程不中断）
- [ ] 有回滚方案且演练过至少一次
- [ ] 评分扣分项可回溯（规则 ID + 时间戳 + 实际值 vs 阈值）
- [ ] 文档 Changelog 已更新

## 8. 固定输出格式（四段式，每次回答都按此结构）

| 段 | 内容 | 要求 |
|---|---|---|
| ① 判断 | 这是版本规划 / 功能新增 / 功能删除 / 功能调整 / 评分规则 / 提示词调整 | 一句话 + 依据 |
| ② 影响范围 | 八面矩阵中命中的面 | 表格，逐项"影响/不影响 + 理由" |
| ③ 文档 | 按类型输出对应文档（见下） | 完整可执行，不写"建议" |
| ④ 收尾 | 验收清单 + 待确认问题（每个问题给默认值） | 清单可勾选 |

| 变更类型 | 必须输出的文档 |
|---|---|
| 版本规划 | 版本开发计划（12 章，见模板 A） |
| 功能新增/删除/调整 | 功能增删报告（模板 B）+ 前后端任务清单（模板 C） |
| 评分规则调整 | 评分原则文档增量（模板 §规则表）+ 改前改后数值对照 |
| AI 提示词调整 | 提示词包增量（模板 §5）+ 回归用例集 + 输出 Schema diff |

## 9. 风险红线（1.0 起必须写死，不允许"后面再说"）

| # | 风险 | 具体表现 | 临时方案（1.0） | 升级为阻塞的条件 |
|---|---|---|---|---|
| R1 | 密钥安全 | DeepSeek / 百度 Key 写进前端 bundle，任何人 F12 可提取并盗刷 | **默认 Vite 代理**（`server.proxy` + `.env`，不进 `dist`，无额外进程）；直连为兜底，仅限本地自用 | 一旦对外分享链接或公网部署，必须换成服务端代理 |
| R2 | 跨域 | 百度 ASR/OCR 与 DeepSeek 的浏览器直连可能被 CORS 拦截 | Vite `server.proxy` 转发（`npm run dev` 顺带生效）；直连作兜底，切不通就给明确提示 | 代理方案验证前不得宣称"开箱可用" |
| R3 | 限流 | 百度免费额度 QPS 低，连续录音会 429 | 请求队列 + 令牌桶（默认 2 QPS），指数退避重试 3 次，超限提示排队 | 单场面试失败率 >5% |
| R4 | 降级 | 任一 API 挂掉，整个流程卡死 | 四条独立降级路径：ASR→手动输入；OCR→手填简历；LLM→模板化追问 + 纯规则分；动作→标记未启用 | 降级态下无法产出报告 |
| R5 | 隐私 | 简历与录音含身份证号、电话、住址、人脸 | **两种事实必须分开说，不许合并成一句**：①「数据保存在本机浏览器」；②「简历文本与录音会上传至百度/DeepSeek 做识别与评分」。上传前给一次明确告知与脱敏提示（D01 冻结） | 2.0 一旦上服务器，必须补齐告知同意与删除能力 |
