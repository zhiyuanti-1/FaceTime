# 产品经理规范（PM-Spec）

> 版本 1.0 ｜ 2026-11-03 ｜ 适用：本产品全部版本（1.0 / 2.0 / 3.0）
> 性质：**PM 的工作规则**，不是产品需求。需求在 [需求](../product/需求.md)，实现约束在 [技术约束](技术约束.md)，节奏在 [开发流程](开发流程.md)。
> 读者：PM 本人（首要）、需求方（次要）。**代码 agent 不需要读本文件。**

**怎么用**：
- 接需求前看 §2，交付前看 §9 和 §10，写文档前看 §4。
- 新增规则写进对应小节，改完在 §13 记一行；不确定的先进 §12 待补充，不要直接改正文。

---

## 1. 角色与决策边界

| 事项 | PM 直接定 | 需需求方拍板 | 需技术确认 |
|---|---|---|---|
| 版本范围、功能清单 | ✅ | 重大取舍 | — |
| 页面、流程、状态机 | ✅ | 关键交互 | 可行性 |
| 数据结构、接口契约 | ✅ 草案 | — | ✅ 最终 |
| 评分维度、权重、阈值 | ✅ 提案 | ✅ 口径 | 数据可得性 |
| 提示词、JSON Schema | ✅ | 拷打尺度 | token 成本 |
| 验收标准 | ✅ | ✅ 签字 | — |
| 排期、人力 | 建议 | ✅ | ✅ |

**底线**：文档是契约，不是建议。写进去的字段名、枚举、错误码、阈值，实现方照做，不再自行解释。

## 2. 需求受理协议

### 2.1 必问两项

| 必问 | 可选值 |
|---|---|
| 目标版本 | `1.0` / `2.0` / `3.0` / `跨版本` / `Hotfix` |
| 变更类型 | `版本规划` / `功能新增` / `功能删除` / `功能调整` / `评分规则` / `提示词` |

### 2.2 没说清时：假设优先，不阻塞

在文档或回复开头写「假设声明（未确认）」，逐条列 `A1/A2` 与「若假设错误会怎样」。
一次最多问 **3 个**“会改变文档结构”的问题，其余给默认值推进。**不许用提问代替交付。**

### 2.3 固定四段输出

① 判断（版本 + 类型）→ ② 八面影响 → ③ 对应文档 → ④ 验收清单 + 待确认（每条带默认值）。

## 3. 变更管理

### 3.1 编号

`CR`（功能）/ `SR`（评分）/ `PR`（提示词）/ `HF`（热修），格式 `<前缀>-<版本>-<3位序号>`。序号只增不复用。

### 3.2 八面影响（逐项写“影响 / 不影响 + 理由”，不许留空）

前端 · 后端 · API 契约 · 数据结构 · 评分规则 · AI 提示词 · 部署运维 · 隐私合规。
命中「评分 / 提示词」，或涉及简历解析、语音、动作、部署时，报告顶部加 **⚠️ 专项标注**。

### 3.3 五步评估（≤70 分钟）

归类 → 八面扫描 → 契约 diff → 回归范围 → 结论（做 / 不做 / 延期 + 置换项 + 回滚）。

### 3.4 状态机与冻结

```
提出 → 评估 → 已确认 → 开发中 → 待验收 → 已上线
                 ↓                  ↓
              已拒绝             已回滚
```

待验收前 3 天起只收 P0 缺陷；上线后 7 天只收四类 Hotfix（不可用 / 数据错 / 密钥泄露 / 隐私事故）。

### 3.5 等量置换

**加一个功能，必须同时回答“减什么”或“延期几天”。** 两者都不给，默认进下一版本。

## 4. 文档纪律

### 4.1 五个入口

| 文件 | 唯一职责 |
|---|---|
| `AGENTS.md` | agent 入口与硬约束 |
| `product/需求.md` | 要做什么（唯一事实源） |
| `docs/技术约束.md` | 怎么实现 |
| `docs/开发流程.md` | 怎么干活 |
| `docs/进度.md` | 到哪一步了 |

本文件是第 6 份，**只给 PM 看**，不进 agent 阅读链。

### 4.2 四条硬规则

1. **一个事实只能有一处**。发现第二处副本，当场合并，不要“两边都更新”。
2. **不新建平级文档**。新内容进既有文件；确实放不下，先在 §12 记录理由。
3. **归档 ≠ 删除**。历史移 `archive/`，并在进度文档记映射；归档不是事实源。
4. **改文件名要同步所有引用**，交付前跑一次链接检查。

## 5. 范围管理

- 每个版本必须写清「本期做 / 本期不做」，不做清单与做清单**同等重要**。
- 非目标要显式写（例：1.0 不做动作识别、不做公网、不做付费）。
- 范围变更必须走 CR，并在进度文档留八面影响与回滚。
- **技术选型变更也算范围变更**（换库、换框架、改部署形态）。

---

## 6. 评分与规则设计

设计一条规则，必须同时给出五件事，缺一不算完成：

| 要素 | 要求 | 反例 |
|---|---|---|
| 触发条件 | 时间窗 + 次数阈值 + 置信度 | “经常出现口头禅” |
| 判定方式 | 可计算的表达式 | “感觉不流畅” |
| 分值 | 具体数字 + 封顶 | “适当扣分” |
| 误判保护 | 低置信度 / 失败 / 遮挡时怎么办 | 无 |
| 可回溯 | 规则 ID + 时间点 + 实际值 vs 阈值 + 原文证据 | 只给总分 |

另外三条铁律：
1. **双引擎分离**：AI 给内容理解分，规则引擎给客观行为分，互不覆盖。
2. **阈值外置**：阈值只在配置文件里，算法与组件内不许出现魔法数。
3. **不可评估不是 0 分**：剔除分母并重新归一化，覆盖率不足只给区间。

## 7. 提示词与 AI 契约

- 输入结构化（岗位 / 简历 / 题目 / 回答 / 历史），输出**只能是 JSON**，不用自然语言兜底。
- 输出必须含：分数、扣分项（带证据）、加分项、追问、疑点、建议、`needsReview`。
- **低置信度不许强行打分**，返回“需复核”。
- 三类禁令：不编造经历与引用；不评价外貌/年龄/性别/婚育/口音；不做人身攻击。
- 每次改提示词都要带回归用例集，跑过再上线，并记 `promptVersion`。

## 8. 排序与优先级

### 8.1 三档定义

| 档 | 定义 | 判据 |
|---|---|---|
| P0 | 缺了产品不成立 | 用户无法完成核心任务 |
| P1 | 能跑通但不好用 | 用户会骂，但用得下去 |
| P2 | 锦上添花 | 用户不会因此放弃 |

### 8.2 排序方法：先闭环，后模块

**错误做法**：按技术模块排队（仓储 → 组卷 → 音频 → AI …），全部做完才第一次看见产品。
**正确做法**：按**能交付给用户的竖切**排队——每个里程碑结束时，用户能完整走一遍。

判据：里程碑的验收语必须是“**用户能做 X 了**”，而不是“模块 Y 写完了”。

### 8.3 紧急 × 重要

| | 重要 | 不重要 |
|---|---|---|
| **紧急** | 立刻做（阻塞主流程 / 数据风险） | 批量做或砍（如样式微调） |
| **不紧急** | 排进里程碑（P1/P2） | 删掉（如提前上队列、多用户） |

**警惕“技术诱惑”**：队列、多租户、对象存储、监控，在单用户阶段全是“不紧急不重要”，提前做就是负债。

## 9. 状态汇报规范

### 9.1 汇报什么

**只汇报用户能感知的状态。** 一行写不出“用户点一下能验证什么”，这行就不该出现。

### 9.2 格式

```
§1 一句话状态（现在能用 / 不能用）
§2 能做什么（现状，不夸大）
§3 P0 未完成（表：功能 | 现状 | 做完的判据）
§4 P1 未完成
§5 P2 可延后
§6 里程碑（M1..M4，每个一句话）
§7 技术现状（≤3 行，附文档链接）
```

### 9.3 禁止项

| 禁止 | 原因 |
|---|---|
| 把 DDL / 驱动 / workspace / 建表 写进功能状态表 | 需求方无法据此判断产品走到哪 |
| 写“已完成验证”但不写验证了什么 | 无法复现 |
| 用“进行中”当状态 | 没有判据 |
| 把技术风险写成产品风险（或反之） | 责任错位 |

### 9.4 每行必须有“做完的判据”

反例：`历史记录 | 开发中`
正例：`历史记录 | 无 | 关掉浏览器重开，那场面试还在`

## 10. 反模式清单（本产品真实踩过）

| # | 症状 | 为什么会发生 | 正确做法 |
|---|---|---|---|
| 1 | 把“示例数值”写成“产品定义”（如内置岗位权重预设） | 为了让文档更具体 | 示例必须标“仅示例、可删、改它不算需求变更” |
| 2 | 把可选项写成“必需组件”（如独立代理进程） | 把安全边界想得比场景更重 | 先问“用户怎么用”，再问“最坏会怎样” |
| 3 | 用人日冒充工期 | 沿用传统排期惯性 | 人日只用于排序；工期由“卡点”决定（联调、内容、真机调参） |
| 4 | 同一口径在多处副本 | 每份文档都“顺手写一遍” | 一处定义 + 其余引用；交付前全局搜关键词 |
| 5 | 算例自己不自洽（4 个 1 说成已满 5） | 写的时候没真算 | 算例必须手算一遍，并写成可执行断言 |
| 6 | 状态汇报混入技术项 | 手上只有技术信息 | 先翻译成“用户能不能用”，技术细节单独一节 |
| 7 | 按模块排期 | 技术上更“整齐” | 按竖切里程碑排，每个里程碑可交付 |
| 8 | 提前上队列 / 多用户 / 公网 | “迟早要做” | 单用户阶段一律延后，写进非目标 |
| 9 | 只给建议，不给可执行文档 | 怕写死 | 文档里写死字段与阈值，改就改文档 |
| 10 | 用提问代替交付 | 想确认清楚 | 给默认值 + 假设声明，先交付再迭代 |
