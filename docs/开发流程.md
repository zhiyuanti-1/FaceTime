## 1. 分工与决策边界

| 事项 | PM 直接定 | 需要需求方拍板 | 需要技术确认 |
|---|---|---|---|
| 版本范围、功能清单 | ✅ | 重大取舍 | — |
| 页面、流程、状态机 | ✅ | 关键交互 | 可行性 |
| 数据结构、接口契约 | ✅（草案） | — | ✅ 最终确认 |
| 评分维度、权重、阈值 | ✅ 提案 | ✅ 口径 | 数据可得性 |
| 提示词、JSON Schema | ✅ | 拷打尺度 | token 成本 |
| 验收标准 | ✅ | ✅ 签字 | — |
| 排期与人力 | 建议 | ✅ | ✅ |

**原则**：文档是契约，不是建议。字段名、枚举、错误码、阈值一旦写进 [需求](../product/需求.md)，实现方按此执行，不再自行解释。

## 2. 需求受理（每次需求的第一步）

### 2.1 必问两项

| 必问项 | 可选值 |
|---|---|
| 目标版本 | `1.0` / `2.0` / `3.0` / `跨版本` / `Hotfix` |
| 变更类型 | `版本规划` / `功能新增` / `功能删除` / `功能调整` / `评分规则` / `提示词` |

### 2.2 没说清时：假设优先，不阻塞

在文档或回复开头写「假设声明（未确认）」，逐条列 A1/A2 及影响；一次最多问 3 个"会改变结构"的问题，其余给默认值推进。

### 2.3 固定输出四段

① 判断（版本+类型）→ ② 八面影响 → ③ 对应文档 → ④ 验收清单 + 待确认（每题带默认值）。

## 3. 变更管理

### 3.1 编号

| 类型 | 前缀 | 格式 | 示例 |
|---|---|---|---|
| 功能变更 | `CR` | `CR-<版本>-<3位>` | `CR-1.0-004` |
| 评分规则 | `SR` | `SR-<版本>-<3位>` | `SR-1.0-001` |
| 提示词 | `PR` | `PR-<版本>-<3位>` | `PR-1.0-002` |
| 热修 | `HF` | `HF-<日期>-<序号>` | `HF-20261110-01` |

### 3.2 八面影响（每项写"影响/不影响 + 理由"，不许留空）

前端 · 后端 · API 契约 · 数据结构 · 评分规则 · AI 提示词 · 部署运维 · 隐私合规。
命中「评分规则 / 提示词」，或涉及简历解析、语音、动作、部署时，报告顶部加 **⚠️ 专项标注**。

### 3.3 五步评估（总耗时 ≤70 分钟）

归类 → 八面扫描 → 契约 diff → 回归范围 → 结论（做/不做/延期 + 置换项 + 回滚方案）。

### 3.4 状态机与冻结窗口

```
提出 → 影响评估 → 已确认 → 开发中 → 待验收 → 已上线
                       ↓                   ↓
                    已拒绝              已回滚
```

| 阶段 | 允许的变更 | 审批 |
|---|---|---|
| 开发期 | 任意，但需"等量置换"或"延期 X 天" | PM |
| 待验收前 3 天 | 仅 P0 缺陷 | PM + 需求方 |
| 验收中 | 仅 P0 缺陷 | 需求方 |
| 上线后 7 天 | 仅 Hotfix（不可用 / 数据错 / 密钥泄露 / 隐私事故） | 需求方 |

### 3.5 回滚分级

| 级 | 场景 | 手段 | 目标时长 |
|---|---|---|---|
| L1 | 阈值/开关错 | 改配置热生效 | ≤5 min |
| L2 | 版本故障 | 切回上一产物 | ≤15 min |
| L3 | 迁移错误 | 反向脚本 + 备份 | ≤2 h |
| L4 | 密钥/隐私事故 | 吊销、关停、全量降级 | ≤5 min |

## 4. 版本节奏（1.0，16 轮 · CR-1.0-007 后含后端）

**每轮 = 一次对话/一个 PR，必须有明确出口。** 小任务（S）一轮可做多个，大任务（L）一轮只做一个。

| 档 | 判据 | 单轮容量 |
|---|---|---|
| S | ≤1h，改一处口径 | 3–5 个 |
| M | 2–4h，跨 2–3 处契约 | 1–2 个 |
| L | 1–2 天，有技术不确定性 | 1 个，先决策再动手 |

| 轮 | 任务 | 档 | 出口 |
|---|---|---|---|
| R1 | 冻结 D02–D08、D11–D14 | S×3+M | ✅ 已完成 |
| R1.5 | 1.0 原型图 9 张 | M | ✅ 已完成 |
| R2 | 契约正文（实体/枚举/状态/错误码） | M×2 | 字段唯一，实现只照抄 |
| R3 | 阈值配置结构 + 纯内核用例表 | M×2 | 阈值外置，12 条用例可判定 |
| R4 | **工程骨架**：npm workspaces（已注册apps/web；apps/api及packages在运行工程落地时加入）+ 前端空页面 + 后端空模块 + 连接现有Oracle FREEPDB1 | **L** | 三进程跑通，`/api/health` 200 |
| R5 | **数据库骨架**：Oracle SQL（7业务表+迁移表已建）+ 受控迁移 + TypeORM仓储 | M×2 | 迁移成功，仓储单测过 |
| R6 | **本地 API 基座**：正常请求处理、输入校验、统一错误码（无登录/JWT，攻击防御留3.0） | M×2 | 正常请求/错误格式一致 |
| R7 | **文件与存储**：音频上传、磁盘 adapter、软删除 + 清理任务 | M×2 | 上传可回放，删除后文件消失 |
| R8 | **简历链路**：上传 → OCR → 解析 → 确认 → 入库 | M×2 | 三种简历都能定稿并落库 |
| R9 | **组卷（服务端）**：配额/抽题/排序/拷打题 + 可复现 seed | **L** | 200 题真跑，同 seed 同结果 |
| R10 | **录音 + ASR**：采集、切段、上传、转写时间戳 | **L** | 三段 fixture 切段正确，转写可对齐 |
| R11 | **规则引擎**：`packages/shared/scoring` 纯内核 + 12 条用例 | **L** | 全绿，前后端共用同一实现 |
| R12 | **AI 评分**：组装/校验/归一/缓存/降级（服务端） | **L** | Schema 不过即拒，失败走规则兜底 |
| R13 | **报告聚合与查询**：六维、覆盖率、区间、报告接口 | **L** | 报告可由 sessionId 重建 |
| R14 | **状态机与断点恢复**：服务端状态 + 前端恢复 | M×2 | 刷新回当前题，已完成不丢 |
| R15 | **页面补全 + 四条降级** | **L** | 四条降级可演示且仍出报告 |
| R16 | 导出、验收清单、回归演练 | M×2 | 验收清单全绿 |

**顺序理由**：

- R4–R7 是后端地基，**必须先于任何业务**；地基没通就写业务，返工率最高。
- R10（音频）仍值得独占一轮：Safari 编码差异、VAD 阈值只能实测。
- R9（组卷）逻辑最密，且有 200 题可真跑，是"一次做对"的窗口。
- **1.0 最大返工风险**：前后端各写一份评分逻辑。必须共用 `packages/shared/scoring`，前端只做展示。

## 5. DoR / DoD

**DoR（不满足不进开发）**：有版本与编号 · 有"本期做/不做" · 有可量化验收 · 八面已填 · 无未决 P0 · 评分/提示词有初稿。

**DoD（不满足不算完成）**：功能逐条验收（附证据）· 契约与实现一致 · 降级可用 · 回滚演练过 · 扣分可回溯 · 文档 Changelog 已更新。

## 6. 文档规则（本仓库，2026-11-03 起生效）

### 6.1 只允许这些 Markdown

| 文件 | 唯一职责 | 谁改 |
|---|---|---|
| `AGENTS.md` | 所有 agent 的入口与硬约束 | 慎改，改需记录 |
| `README.md` | 5 行索引，指向下面 4 个 | PM |
| `product/需求.md` | **唯一需求事实源** | PM |
| `docs/开发流程.md` | 本文件：怎么干活 | PM |
| `docs/进度.md` | 现在到哪一步、下一步、未决 | PM，每轮更新 |
| `docs/技术约束.md` | 架构/目录/编码/接口/安全/测试/部署 | 技术 |
| `product/prototype/README.md` | 原型图索引（图给 agent 读） | PM |

### 6.2 硬规则

1. **不再新建根级规范文档**。新增内容写进上述 5 份之一；确实放不下的，先在 `进度.md` 提"需要第 6 份"，批准后再建。
2. **每个目录不再单独放 README**。目录职责统一写在 [技术约束](技术约束.md) §2 的表里。
3. **变更记录**写在对应文件的文末表格，不单独开文件。
4. **归档不等于删除**：历史文件移到 `docs/archive/`，并在 [进度](进度.md) §5 记录映射。归档文件不是事实源。
5. 文档里的相对链接必须能解析；改文件名要同步所有引用。

### 6.3 为什么这样改

71 份 Markdown 里，只有 4 类信息是 agent 真正需要的：**要做什么、怎么做、做到哪、有哪些硬约束**。其余是同一信息的多处副本，副本会漂移，漂移会产生矛盾——之前 `java 出 0 道` 就是这么来的。
