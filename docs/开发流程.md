## 1. 分工与决策边界

| 事项 | PM 直接定 | 需要需求方拍板 | 需要技术确认 |
|---|---|---|---|
| 版本范围、功能清单 | ✅ | 重大取舍 | — |
| 页面、流程、状态机 | ✅ | 关键交互 | 可行性 |
| 数据结构、接口契约 | ✅（草案） | — | ✅ 最终确认 |
| 评分维度、权重、阈值 | ✅ 提案 | ✅ 口径 | 数据可得性 |
| 提示词、JSON Schema | ✅ | 拷打尺度 | token 成本 |
| 验收标准 | ✅ | ✅ 签字 | — |
| 排期与人力 | 建议 | ✅ | ✅ |

**原则**：文档是契约，不是建议。字段名、枚举、错误码、阈值一旦写进 [需求](../product/需求.md)，实现方按此执行，不再自行解释。

## 2. 需求受理（每次需求的第一步）

### 2.1 必问两项

| 必问项 | 可选值 |
|---|---|
| 目标版本 | `1.0` / `2.0` / `3.0` / `跨版本` / `Hotfix` |
| 变更类型 | `版本规划` / `功能新增` / `功能删除` / `功能调整` / `评分规则` / `提示词` |

### 2.2 没说清时：假设优先，不阻塞

在文档或回复开头写「假设声明（未确认）」，逐条列 A1/A2 及影响；一次最多问 3 个"会改变结构"的问题，其余给默认值推进。

### 2.3 固定输出四段

① 判断（版本+类型）→ ② 八面影响 → ③ 对应文档 → ④ 验收清单 + 待确认（每题带默认值）。

## 3. 变更管理

### 3.1 编号

| 类型 | 前缀 | 格式 | 示例 |
|---|---|---|---|
| 功能变更 | `CR` | `CR-<版本>-<3位>` | `CR-1.0-004` |
| 评分规则 | `SR` | `SR-<版本>-<3位>` | `SR-1.0-001` |
| 提示词 | `PR` | `PR-<版本>-<3位>` | `PR-1.0-002` |
| 热修 | `HF` | `HF-<日期>-<序号>` | `HF-20261110-01` |

### 3.2 八面影响（每项写"影响/不影响 + 理由"，不许留空）

前端 · 后端 · API 契约 · 数据结构 · 评分规则 · AI 提示词 · 部署运维 · 隐私合规。
命中「评分规则 / 提示词」，或涉及简历解析、语音、动作、部署时，报告顶部加 **⚠️ 专项标注**。

### 3.3 五步评估（总耗时 ≤70 分钟）

归类 → 八面扫描 → 契约 diff → 回归范围 → 结论（做/不做/延期 + 置换项 + 回滚方案）。

### 3.4 状态机与冻结窗口

```
提出 → 影响评估 → 已确认 → 开发中 → 待验收 → 已上线
                       ↓                   ↓
                    已拒绝              已回滚
```

| 阶段 | 允许的变更 | 审批 |
|---|---|---|
| 开发期 | 任意，但需"等量置换"或"延期 X 天" | PM |
| 待验收前 3 天 | 仅 P0 缺陷 | PM + 需求方 |
| 验收中 | 仅 P0 缺陷 | 需求方 |
| 上线后 7 天 | 仅 Hotfix（不可用 / 数据错 / 密钥泄露 / 隐私事故） | 需求方 |

### 3.5 回滚分级

| 级 | 场景 | 手段 | 目标时长 |
|---|---|---|---|
| L1 | 阈值/开关错 | 改配置热生效 | ≤5 min |
| L2 | 版本故障 | 切回上一产物 | ≤15 min |
| L3 | 迁移错误 | 反向脚本 + 备份 | ≤2 h |
| L4 | 密钥/隐私事故 | 吊销、关停、全量降级 | ≤5 min |

## 4. 版本节奏（1.0，16 轮 · CR-1.0-007 后含后端）

**每轮 = 一次对话/一个 PR，必须有明确出口。** 小任务（S）一轮可做多个，大任务（L）一轮只做一个。

| 档 | 判据 | 单轮容量 |
|---|---|---|
| S | ≤1h，改一处口径 | 3–5 个 |
| M | 2–4h，跨 2–3 处契约 | 1–2 个 |
| L | 1–2 天，有技术不确定性 | 1 个，先决策再动手 |

- R4–R7 是后端地基，**必须先于任何业务**；地基没通就写业务，返工率最高。
- R10（音频）仍值得独占一轮：Safari 编码差异、VAD 阈值只能实测。
- R9（组卷）逻辑最密，且有 200 题可真跑，是"一次做对"的窗口。
- **1.0 最大返工风险**：前后端各写一份评分逻辑。必须共用 `packages/shared/scoring`，前端只做展示。

## 5. DoR / DoD

当前开发期验证策略（用户2026-11-06确认）：新功能或缺陷修复只验证本批功能及关键失败恢复；不要求每轮跑全量测试。后文历史轮次命令是当时验收记录，不构成当前每轮必跑清单。

**DoR（不满足不进开发）**：有版本与编号 · 有"本期做/不做" · 有可量化验收 · 八面已填 · 无未决 P0 · 评分/提示词有初稿。

**DoD（不满足不算完成）**：功能逐条验收（附证据）· 契约与实现一致 · 已批准的兼容或降级路径可用 · 适用时验证回滚和扣分追溯 · 文档变更记录已更新。

## 6. 文档规则（本仓库，2026-11-03 起生效）

### 6.1 只允许这些 Markdown

| 文件 | 唯一职责 | 谁改 |
|---|---|---|
| `AGENTS.md` | 所有 agent 的入口与硬约束 | 慎改，改需记录 |
| `README.md` | 5 行索引，指向下面 4 个 | PM |
| `product/需求.md` | **唯一需求事实源** | PM |
| `docs/开发流程.md` | 本文件：怎么干活 | PM |
| `docs/进度.md` | 现在到哪一步、下一步、未决 | PM，每轮更新 |
| `docs/技术约束.md` | 架构/目录/编码/接口/安全/测试/部署 | 技术 |
| `product/prototype/README.md` | 原型图索引（图给 agent 读） | PM |

### 6.2 硬规则

1. **不再新建根级规范文档**。新增内容写进上述 5 份之一；确实放不下的，先在 `进度.md` 提"需要第 6 份"，批准后再建。
2. **每个目录不再单独放 README**。目录职责统一写在 [技术约束](技术约束.md) §2 的表里。
3. **变更记录**写在对应文件的文末表格，不单独开文件。
4. **归档不等于删除**：历史文件移到 `docs/archive/`，并在 [进度](进度.md) §5 记录映射。归档文件不是事实源。
5. 文档里的相对链接必须能解析。改文件名时同步所有引用。
6. README、设计、使用说明、接口文档和注解说明使用中文。标识符、协议字段和第三方固定名称沿用原文。确需保留英文自然语言时，记录原因和范围。
7. 功能新增、修改或删除的同一批次更新文档。删除接口、字段、配置或注解时，一并删除现行说明、示例和引用，并检查 OpenAPI 与实际契约是否一致。

### 6.3 为什么这样改

71 份 Markdown 里，只有 4 类信息是 agent 真正需要的：**要做什么、怎么做、做到哪、有哪些硬约束**。其余是同一信息的多处副本，副本会漂移，漂移会产生矛盾——之前 `java 出 0 道` 就是这么来的。

## 强制双对话交付（CR-1.0-012）

以后功能修改必须按两次对话执行：
1. **后端对话**：先读最新产品文档/原型并记录差异，定义共享运行时契约，完成后端/迁移/错误与降级/测试，写清接口路径、请求响应、验收结果、未实现项和下一次前端接入清单。此阶段禁止改apps/web的页面、路由或调用实现。
2. **前端对话**：以前一对话已验证接口与共享契约为准，组件化实现/接入前端、检查桌面与窄屏、完成端到端验收；发现缺口记录后回到后端修订，禁止前端硬编码数据或偷偷补业务规则。

后端阶段可运行既有前端检查以识别契约影响。需变更前端调用时，在后端交接中列出替代路径和接入顺序。只有用户明确改变本次分工，才可同对话跨端。无需反复询问已授权动作；不自动新建聊天、提交或推送。

## AI小步迭代（CR-1.0-015）

目标：减少大批代码生成后的失控修改。以下步骤适用于前后端各自对话，不增加逐批用户审批；已授权范围由agent连续完成。技术清单见[技术约束](技术约束.md)§17/§18。

### 开工任务卡（可复制完善）

```text
版本/编号/本轮端：
唯一目标（用户能完成什么）：
本批范围 / 不包含：
必须保留的行为与视觉：
需求章节 / 现有实现 / 复用入口：
接口变化 / 数据变化 / 八面评估：
预计修改文件及各自原因：
验收：输入 → 操作 → 可观察结果（成功、失败、恢复）：
验证命令 / 浏览器步骤 / 测试环境：
风险 / 回退方式 / 待确认业务口径：
```

1. **建立基线**：检查git status与相关diff，标出用户已有修改；阅读调用方/被调用方与相关测试，记录当前缺陷和已认可行为。必要时先复现，不能根据猜测整页重写。
2. **划分批次**：一批一个可独立验证的行为，例如“保存失败保留答案”，不是“一次重做所有练习页”。默认预计超过5个手写实现文件先拆批或说明不可拆的依赖；测试/契约/必要文档可随批更新，不以数量代替职责判断。
3. **先做最小样例**：后端按契约→用例→持久化/适配器→测试；前端按client→Hook→一个页面→浏览器验证。样例通过后再推广，禁止先复制十处再一起修错。
4. **改后立即核对**：检查本批diff、针对性测试和相邻旧行为；改公共组件查所有调用者，改契约查两端使用处，改样式核对关联视口。新增回归先修好再扩下一批。
5. **修改请求先分类**：功能缺陷、视觉微调、契约调整、结构重构分别列范围；“按钮间距”不顺便改请求，“修保存”不重写布局。确需扩大时记录原因、风险及新验收；业务取舍未明确才问用户。
6. **停止无证据试错**：同一问题连续两次修改未改善，暂停继续补丁，重新收集复现、调用链、网络/状态证据；提出新根因后再改，不堆CSS覆盖、重试或类型断言。
7. **收尾**：当前开发期以功能跑通为目标，按受影响行为做小批量验证，必要时执行类型检查或构建；不默认执行完整check/全量测试，不扩测试体系。记录实际结果及未运行项；保留已有测试资产，不删除门禁或全仓格式化来刷绿。公开提交前仍核对保密要求。
8. **交接与回退**：进度记录本批文件、实现/验证/未完成及下一步。回退只撤本轮可识别改动，保留用户修改；禁止reset --hard、覆盖整文件或删库式回退。没有提交时用diff逐块回退，不伪造可恢复提交点。

### 每批交付记录（复制到进度，不新建文档）

```text
批次/编号：
改了什么 / 为什么：
清单结果：FE或BE编号 → 通过/失败/不适用＋证据
保留行为回归：
命令与退出结果 / 未运行及原因：
剩余缺口 / 下一批 / 回退范围：
```

### 架构维护与例外评审（CR-1.0-018）

发现直接影响交付的废弃逻辑或不合理架构时，先评估删除、合并或调整职责。必要的破坏性变更须说明影响的调用方、已有数据与配置、迁移步骤和回退边界。涉及整体设计调整时，先提交 Mermaid 方案并取得确认。实现后验证构建、测试与受影响调用链，确认现行文档和示例已同步。
